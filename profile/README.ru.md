## Обзор проекта

**OpenHarness DSH Plugins** — это сообщество рабочих пространств для пациентов и плагинов, создаваемое совместно xtra-care community и [Dataelem](https://github.com/dataelement). Рабочие пространства работают на базе [DSH Desktop](https://github.com/dataelement/dsh-desktop) (поддерживаемого Dataelem) и организуют медицинские документы, историю болезни и подготовку к врачебным приёмам вокруг реальных жизненных сценариев пациента.

**DSH Desktop by Dataelem** — это настольное агентное приложение, разработанное командой Dataelem на основе upstream-проекта [DeepSeek Harness](https://github.com/deepseek-ai/dsh); оно не является официальным настольным продуктом DeepSeek. xtra-care community привносит пациентские сценарии и предметную экспертизу, а Dataelem предоставляет настольную среду исполнения, фреймворк рабочих пространств и продуктовую поддержку — вместе стороны совершенствуют эталонные образцы и переиспользуемый каркас разработки.

В основе нашей работы лежит принцип **«благотворительность и открытый исходный код»**. Флагманский проект **XiaoYiBao（小胰宝）** и рабочие пространства по отдельным нозологиям сосредоточены на систематизации информации, ведении хронологии болезни, отслеживании показателей и подготовке к консультациям, помогая пациентам и их семьям чётче управлять документами и формулировать вопросы врачу. Рабочие пространства не ставят диагнозы, не дают лечебных или клинических рекомендаций и не заменяют решение врача.

**Ключевые цели:**

- **Открытая экосистема**: открыта для исследователей, клинических инженеров и разработчиков — любой желающий может создавать плагины по единому стандарту.
- **Безопасность и объяснимость**: ответы сопровождаются подтверждающими доказательствами и ссылками на источники; конфиденциальность — главный приоритет, исключающий утечку идентифицирующих данных.
- **Высокая расширяемость**: модульный механизм плагинов позволяет легко подключать новые модели, источники данных и сценарии.
- **Движение силами сообщества**: поощрение совместного участия клиницистов, исследователей и разработчиков, чтобы технологии служили мостом между людьми и надеждой.

## Границы текущей версии и приглашение к соавторству

### Сразу уточним: не все заболевания готовы «из коробки»

- **Редкие заболевания и часть ещё не охваченных сообществом видов рака**: находятся на стадии каркаса, проектирования или набора участников; функциональность и контент неполны.
- **Уже опубликованные рабочие пространства**: уровень зрелости различается — одни пригодны для повседневного использования, другие представляют собой лишь базовый рабочий прототип.
- **Разные рабочие пространства**: модели данных, поля и возможности импорта/парсинга могут отличаться; ориентируйтесь на соответствующий README и статусы в [PROJECTS.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/PROJECTS.md) / [BACKLOG.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/BACKLOG.md).

### Маркеры зрелости

| Маркер | Значение |
| --- | --- |
| 🟢 | Ранняя версия сообщества готова к использованию: базовый сценарий проходит полностью, есть реальное применение в сообществе, продолжается итеративная доработка |
| 🔵 | В разработке: основной функционал реализован, продолжается отладка на реальных устройствах |
| 🟡 | В проектировании / начальная версия: каркас или прототип, сценарий ещё не завершён |
| ⚪ | Задача взята в работу, ожидает начала разработки |
| ⬜ | Набор участников: пока нет постоянного мейнтейнера |

### Ограничения возможностей продукта (прочтите в первую очередь)

- **Не является медицинским изделием**: не выполняет диагностику, не даёт рекомендаций по лечению или оценке эффективности, не заменяет госпитальные системы и врачей.
- **Успешный парсинг ≠ успешная структуризация**: на результаты MinerU/OCR влияют качество оригинала, лимиты токенов / согласие пользователя и тип документа; возможен возврат 0 кандидатов — тогда требуется просмотр распознанного текста или ручной ввод.
- **ИИ только «читает и предлагает кандидатов»**: не записывает данные напрямую в базу фактов; принятие, редактирование или отклонение выполняет человек.
- **Автоматическое сохранение ответов ИИ ещё не замкнуто**: публичный контракт сессий поддерживает только черновики и отправку, без события завершения ответа; сейчас используется «ручной импорт / вставка ответа», а автоматический парсинг появится после добавления хостом события `completed`.
- **База знаний, пакетный импорт, работа с несколькими файлами и ИИ-извлечение всё ещё развиваются**: присутствуют не во всех рабочих пространствах.
- **Данные по умолчанию хранятся локально**: облачный парсинг и внешние API требуют согласия пользователя с явным указанием объёма передаваемых данных.
- **Охват заболеваний неполный**: не следует воспринимать систему как продукт, где «прямо сейчас готово любое заболевание».

### Цель первого релиза: дать соавторам удобную ступень для старта

Мы хотим, чтобы это был не «анонс готового коробочного продукта», а **доступная стартовая ступень**:

- **Партнёры из сообществ редких заболеваний**: приходите со знанием специфики болезни, дополняйте процессы, поля, формулировки и реальные сценарии.
- **Разработчики**: добавляйте модули, интегрируйте OCR/MinerU/базы знаний/API, исправляйте ошибки.
- **Родственники пациентов / волонтёры**: тестируйте, проводите интервью, вычитывайте материалы, организуйте обучение — для вклада не обязательно уметь программировать.
- **Медицинские специалисты / исследователи**: проверяйте медицинскую логику и обозначайте границы того, что система не должна и не может делать.

С чего начать: изучите текущие проекты в [PROJECTS.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/PROJECTS.md) → посмотрите пробелы и свободные задачи в [BACKLOG.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/BACKLOG.md) → выберите направление в [CONTRIBUTING.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/CONTRIBUTING.md) → проверьте шлюзы качества и чек-лист PR в [CONTRIBUTING-WORKBENCH.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/CONTRIBUTING-WORKBENCH.md).

## Основные возможности

1. **Рабочие пространства DSH Desktop** — размещение специализированных панелей по заболеваниям и плагинов внутри настольной среды.
2. **Ориентация на реальные сценарии пациентов** — опираясь на эталонные рабочие пространства вроде XiaoYiBao, последовательно совершенствуем процессы управления информацией для пациентов и их близких.
3. **Прослеживаемость источников** — медицинский контент снабжается указанием источника и версии; непроверенные данные явно помечаются; клинические рекомендации не генерируются.
4. **Систематизация выписок и показателей** — инструменты для структурирования истории болезни, результатов обследований и вопросов к врачу; конкретный объём поддержки зависит от описания и статуса проверки каждого рабочего пространства.
5. **Расширяемый механизм плагинов** — подключение сторонних плагинов через секцию `insert` в `cordis.patch.yml` или встроенный установщик DSH; внутри DSH Desktop используется только встроенный каталог рабочих пространств / список установленных плагинов без запуска отдельного веб-интерфейса.
6. **Многоязычность и локализация** — встроенная китайская локализация с постоянным расширением поддержки новых языков в документации и интерфейсе.

## Обзор архитектуры

**Рабочее пространство — это ядро: снизу оно опирается на базовые сервисы, сверху обеспечивает клиентские приложения; взаимодействие с ИИ двустороннее, а MinerU отвечает исключительно за парсинг.**

```text
┌────────────────────────────────────────────────────────────────────┐
│ Уровень клиентских приложений                                      │
│   Harness Web UI (внутри Desktop; автономный Web требует отд. деплоя)│
│   DSH Desktop (панель рабочего пространства) · В будущем: моб./мини-приложения (через API хоста)│
└───────────────────────────────┬────────────────────────────────────┘
                                │
┌───────────────────────────────▼────────────────────────────────────┐
│ Ядро рабочего пространства                                         │
│   Оболочка: customFrame / привязка нативных сессий / права и аудит │
│   Бизнес-логика: мультипрофили · история и показатели · разбор     │
│         документов · подготовка к приёму · сверка кандидатов · экспорт│
│         психологическая поддержка (сопровождение → паллиатив → горе)│
│         нутритивная поддержка · подбор клин. исследований          │
│         справочник препаратов · управление осложнениями · новые сценар.│
└───────┬───────────────────┬───────────────────┬────────────────────┘
        │ Двусторонний      │ Оригиналы/пакетно │ Поиск/индексация
┌───────▼────────┐  ┌───────▼────────┐  ┌───────▼────────┐
│ Интеграция ИИ  │  │ MinerU (внеш.) │  │ База знаний    │
│ Натив. сессии  │  │ OCR/макет/табл.│  │ Файлы + FTS5   │
│ Фонов. задачи  │  │ markdown/JSON  │  │ Вектор. поиск  │
│ (в планах)     │  │                │  │ (в будущем)    │
└───────┬────────┘  └───────┬────────┘  └───────┬────────┘
        │                   │                   │
┌───────▼───────────────────▼───────────────────▼────────────────────┐
│ Будущие API: knows API · XYB RAG API · мульти-OCR · психология/питание/снимки/генетика│
└────────────────────────────────────────────────────────────────────┘
```

- **ИИ ↔ Рабочее пространство**: рабочее пространство передаёт промпты, подтверждённые факты и фрагменты поиска в нативную сессию; ИИ возвращает только кандидатов и пояснения, не записывая данные напрямую в базу фактов.
- **Конвейер MinerU**: оригинальные документы → пакетный парсинг MinerU → markdown/content_list → `parsed/<docId>.md` + кандидаты → подтверждение человеком → слой фактов SQLite.
- **Среда выполнения**: это логическая схема слоёв, а не граф процессов; рабочее пространство — это плагин DSH внутри профиля: серверная часть работает в процессе Harness, панель — в Harness Web UI, бизнес-страницы — в iframe, нативные сессии передаются хостом, а данные хранятся в собственном workspace рабочего пространства. Подробнее см. [ARCHITECTURE.md §2.2](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/ARCHITECTURE.md#22-运行时映射工作台作为-dsh-插件).
- **Слой данных**: база SQLite рабочего пространства хранится в выбранной пользователем папке документов (например, `pinkypal.sqlite`), а не в профиле DSH и не в базе сессий; ИИ не открывает её напрямую.
- **Запись от ИИ**: ответы ИИ формируют только кандидатов, которые попадают в SQLite только через API рабочего пространства после подтверждения человеком; по умолчанию инструменты прямой записи SQL/кода не предоставляются, а фронтенд не изменяется.
- Полная архитектура и низкоуровневый путь записи ИИ в SQLite описаны в **[ARCHITECTURE.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/ARCHITECTURE.md)**.

### Системные требования

| Компонент | Требования | Примечание |
| --- | --- | --- |
| **DSH Desktop** | Последняя стабильная версия | **Рекомендуемая платформа**. Установка и загрузка рабочих пространств и плагинов выполняются внутри приложения; Node и pnpm уже встроены |
| Node.js | ≥ 18 (рекомендуется 20 LTS) | **Требуется только для разработки или CLI**, пользователям Desktop устанавливать не нужно |
| Пакетный менеджер | pnpm (встроен в Desktop) | Для сборки пакетов используйте `pnpm pack` |
| Git | Любая актуальная версия | Клонирование репозиториев и участие в разработке |

### Установка (DSH Desktop, рекомендуемый способ)

1. Установите и запустите **DSH Desktop** с [официального сайта DSH Desktop](https://dshdesktop.com/zh/), завершите первичную настройку.
2. Перейдите в **Настройки → Общие** (Settings → General) и убедитесь, что опция «Включить функции рабочего пространства» активна (при её отключении рабочие пространства не загружаются, но существующие сессии и данные сохраняются).
3. Откройте **Маркет рабочих пространств** (Workbench Market) слева, найдите нужное рабочее пространство (например, «小粉宝» / PinkyPal) и установите его.
4. При появлении уведомления «Изменения установки рабочего пространства вступят в силу после перезапуска Harness» нажмите **Перезапустить сейчас**; если уведомления нет, используйте меню **Harness → Перезапустить Harness**.
5. Вернитесь в маркет, переключитесь на вкладку **Установленные**, проверьте наличие записи и откройте панель через закреплённый вход слева.

> ⚠️ **Не используйте `dsh web` для запуска веб-версии и не включайте плагины через браузер (Settings → Plugins).** Это CLI/Web-среда с другим экземпляром Harness и другой директорией установки — установленное там не загрузится в DSH Desktop. Единственный штатный вход для Desktop — внутренний «Маркет рабочих пространств / Установленные».

### Установка из командной строки (для разработчиков / локального тестирования)

Desktop поставляется со встроенными Harness и pnpm. При установке из командной строки необходимо явно указать каталог Harness **именно этого приложения**, иначе пакет установится в CLI-профиль `~/.dsh` (и Desktop его не увидит):

```bash
# macOS: каталог Harness для Desktop (для других ОС см. окно «О программе / Диагностика»)
export DSH_HOME="$HOME/Library/Application Support/dsh-desktop/harness"
export PATH="$DSH_HOME/.desktop-bin:$PATH"   # использовать встроенные в приложение pnpm / node

dsh plugin add --help                        # сверяйтесь с локальным help, не угадывайте флаги
dsh plugin add ./dist/my-workbench-0.1.0.tgz
```

После установки всё равно необходимо перезапустить Harness внутри приложения и проверить запись во вкладке «Установленные». **Наличие в текущей версии приложения кнопки локальной установки `.tgz` уточняйте непосредственно в разделе «Маркет рабочих пространств / Установленные»**; если её нет, используйте приведённые выше команды CLI.

> Три частые ловушки:
> ① **Harness у Desktop — это не `~/.dsh`**. В macOS по умолчанию используется `~/Library/Application Support/dsh-desktop/harness`, причём папка активного профиля тоже называется `web` — имя совпадает, но расположение другое. То, что установлено в `~/.dsh/profiles/*`, в Desktop не загрузится. Ориентируйтесь на путь из окна «О программе / Диагностика» и фактические логи загрузки, а не на имя папки.
> ② Появление слоя плагина в выводе `dsh --profile web --dump-config` доказывает лишь применение конфигурации, но **не** является доказательством загрузки UI.
> ③ Рабочее пространство должно пройти изолированную generation-установку Desktop и получить запись в `desktop-workbenches/market-installs.json`, чтобы клиент распознал его статус; ручное копирование в `node_modules` не добавит вход в левое меню.

### Проверка успешности установки

| Уровень проверки | Как проверить | Что подтверждает |
| --- | --- | --- |
| Уровень конфигурации | Слой плагина присутствует в `dump-config` | Подтверждает только применение patch |
| Уровень списка | Запись появилась во вкладке «Установленные» внутри приложения | Подтверждает распознавание и регистрацию пакета |
| Уровень интерфейса | Панель открывается из левого меню, основные сценарии кликабельны | **Единственное доказательство успешной установки** |

Необходимы все три уровня; если пройдены только первые два, указывайте «конфигурация загружена, UI не проверен», а не «установка пройдена».

## Дорожная карта рабочих пространств пациентов (цели разработки и набор участников)

Мы создаём рабочие пространства формата «local-first» для конкретных заболеваний (систематизация истории болезни · отслеживание показателей · подготовка к приёму; данные пациента не загружаются скрытно, а при обращении к внешним моделям или сервисам явно указывается объём передаваемой информации). Целевой пул ориентирован на **каталог нозологий NCCN Guidelines® (67 позиций)** и **«Руководство по диагностике и лечению 86 редких заболеваний (издание 2025 года)»** (всего **153 позиции**), чтобы пациенты могли самостоятельно вести записи, а врачи — быстро анализировать ситуацию и взаимодействовать с пациентом.

**153 цели не означают 153 полных цикла с нуля**: они разделены на уровни `T0 семейный эталон / T1 стандарт / T2 шаблонизация / T3 привязка / T4 лист наблюдения` и развиваются волнами; в конце каждой волны закладывается окно обратной связи на 1–2 недели для переноса опыта в общий каркас. Подробности см. в [PROGRAM-PLAN.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/PROGRAM-PLAN.md).

## Руководство по участию

Мы приветствуем любые формы вклада: код, документацию, переводы, обратную связь в Issue и инкубацию новых плагинов.

**Подробное руководство по участию в разработке рабочих пространств см. в [CONTRIBUTING-WORKBENCH.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/CONTRIBUTING-WORKBENCH.md)** — там описаны четыре пути вклада (кураторство нозологии / модули / контент и медицинская выверка / каркас), три шлюза качества, чек-лист самопроверки PR и чек-лист ревью.

### Порядок внесения вклада

1. **Возьмите или создайте Issue**: найдите или откройте задачу в [Issues](https://github.com/xyb-openharness-dsh-plugins/.github/issues) для обсуждения требований и подхода; чтобы взять заболевание в работу, используйте шаблон «病种认领» и оставьте комментарий `/claim` в Issue.
2. **Сделайте Fork и создайте ветку**: ответвитесь от `main` целевого репозитория, назвав ветку, например, `feat/your-feature` или `fix/your-bug`.
3. **Локальная разработка и тестирование**: придерживайтесь стандартов плагинов и стиля кода организации; убедитесь, что проходят базовые проверки и тесты (`npm run check`).
4. **Оформление коммитов**: рекомендуется следовать формату [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:` и т. д.).
5. **Отправка Pull Request**: опишите мотивацию, область изменений и способ проверки; если изменения касаются медицинских материалов, отдельно укажите меры по безопасности и защите приватности.
6. **Ревью и слияние**: требуется одобрение минимум одного мейнтейнера; изменения, затрагивающие шлюзы качества или контракты данных, требуют одобрения двух мейнтейнеров.

> ⚠️ **Критерий качества**: успешное прохождение `npm run check` — это только V1; также необходимы V2 (реальная загрузка в профиле Desktop) и V3 (сквозной рабочий сценарий на реальной машине). **Без всех трёх уровней проверка не считается пройденной.** **«PR смёржен» не означает «выпущено в продакшен / проверено».**

### Четыре незыблемых правила

1. Не давать диагностических и лечебных рекомендаций (не писать «рекомендуется лечение / возможен рецидив / можно отменить препарат / не нужно к врачу / процент излечения»).
2. Хранение данных пациента преимущественно локально (local-first), без скрытой отправки в сеть.
3. Указывать источник и версию для медицинских материалов; неподтверждённые данные помечать как «Не проверено», без экстраполяции с похожих заболеваний.
4. Не копировать клиническое содержание руководств — ссылаться только на название нозологии и версию руководства как ориентир охвата.

### Кодекс поведения

Пожалуйста, сохраняйте дружелюбие, профессионализм и инклюзивность. Мы придерживаемся общепринятых норм поведения в open-source сообществах и не допускаем никаких форм преследования или дискриминации.

### Подпись и лицензирование

Перед отправкой вклада ознакомьтесь с фактической лицензией и условиями участия целевого репозитория и убедитесь, что имеете право передавать код на этих условиях; для репозиториев без опубликованной лицензии предварительно уточните условия у мейнтейнеров.

## Разработка плагинов

Плагин DSH по сути является npm-пакетом, соответствующим спецификации [cordis](https://github.com/cordiverse/cordis). Ниже приведён минимальный рабочий каркас плагина.

### Минимальный пример плагина

`package.json`:

```json
{
  "name": "@your-scope/dsh-plugin-hello",
  "version": "0.1.0",
  "type": "module",
  "main": "lib/index.js",
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.1"
  }
}
```

`src/index.ts` (скомпилированный результат выводится в `lib/index.js`):

```ts
import { Context } from '@deepseek-ai/cordis'

export const name = 'hello'
export const using = [] as const

export function apply(ctx: Context) {
  ctx.on('ready', () => {
    console.log('Hello from your DSH plugin!')
  })
}
```

### Регистрация в конфигурации DSH

После установки пакета в `node_modules` целевого профиля он подключается через секцию `insert` файла `cordis.patch.yml`:

```yaml
# <целевой профиль>/cordis.patch.yml
- insert:
    - id: hello
      name: '@your-scope/dsh-plugin-hello'
```

Способ установки зависит от **целевой среды** (они не взаимозаменяемы):

| Среда | Способ установки | Целевой профиль (ориентируйтесь на фактическую загрузку) |
| --- | --- | --- |
| DSH Desktop | Рабочее пространство: найдите и установите в «Маркете рабочих пространств» слева, затем перезапустите Harness<br>Локальное тестирование: укажите `DSH_HOME` на Desktop Harness и выполните `dsh plugin add` | По умолчанию `~/Library/Application Support/dsh-desktop/harness/profiles/web`, **а не** `~/.dsh` |
| CLI / Web | Проверьте синтаксис через `dsh plugin add --help` и установите | `~/.dsh/profiles/web` |

> Рабочие пространства (`workbench`) **можно** устанавливать только на стороне Desktop: помимо бандла, они должны пройти изолированную generation-установку Desktop и получить запись в `desktop-workbenches/market-installs.json`, чтобы клиент распознал их как рабочее пространство. При простом копировании в `node_modules` вход не появится в левом меню и не отобразится в разделе «Установленные».

Соглашения по разработке:

- Рекомендуется именовать пакет плагина по шаблону `@<scope>/dsh-plugin-<name>` для удобства идентификации и группировки.
- Указывайте в `peerDependencies` только необходимые зависимости (например, `@deepseek-ai/cordis` и соответствующие `@deepseek-ai/dsh-client-*`), чтобы избежать дублирования бандла с хостом.
- В чувствительных сценариях (например, медицинских) вывод должен быть объяснимым, прослеживаемым и ориентированным на приватность по умолчанию.
