## プロジェクト概要

**OpenHarness DSH Plugins** は、xtra-care communityと [Dataelem（データエレム）](https://github.com/dataelement) が共同で構築する患者ワークベンチおよびプラグインコミュニティです。ワークベンチは Dataelem が保守する [DSH Desktop](https://github.com/dataelement/dsh-desktop) 上で動作し、患者さんの実際のシーンに沿って資料・病歴・受診準備を整理します。

**DSH Desktop by Dataelem** は、Dataelem チームがアップストリームの [DeepSeek Harness](https://github.com/deepseek-ai/dsh) をベースに開発したデスクトップ Agent アプリケーションであり、DeepSeek 公式のデスクトップ製品ではありません。xtra-care communityが患者シーンと業務知見を提供し、Dataelem がデスクトップホスト・ワークベンチフレームワーク・製品化サポートを提供することで、双方がテンプレートと再利用可能なスキャフォールドを共同で整備しています。

私たちは「**公益とオープンソース**」を核とし、フラッグシッププロジェクト **小胰宝（XiaoYiBao）** および各疾患ワークベンチを通じて、情報整理・病歴記録・指標追跡・受診準備に注力し、患者さんとご家族が資料や質問事項をより明確に管理できるよう支援します。ワークベンチは診断・治療・処置の提案を行わず、医師の判断を代替するものではありません。

**主な目標：**

- **オープンなエコシステム**：研究者・臨床エンジニア・開発者に開かれており、誰もが統一された規約に基づいてプラグインを貢献できます。
- **安全性と説明可能性**：出力には根拠となるエビデンスと参照元を明記し、プライバシーを最優先して個人識別情報の漏洩を防ぎます。
- **高い拡張性**：モジュール式のプラグイン機構により、新しいモデル・データソース・シーンを容易に連携できます。
- **コミュニティ主導**：臨床・研究・開発の協働を促し、テクノロジーを人と希望をつなぐ架け橋にします。

## 現バージョンの範囲と共同開発のご案内

### はじめに：すべての疾患がそのまま使えるわけではありません

- **希少疾患および未カバーの一部のがん種**：まだスケルトン・設計・募集段階であり、機能やコンテンツは不完全です。
- **公開済みワークベンチ**：成熟度は均一ではなく、日常的に利用できるものもあれば、動作確認ができる程度の初期版もあります。
- **ワークベンチ間の違い**：データモデル・項目・インポート／解析機能はワークベンチごとに異なる場合があります。それぞれの README および [PROJECTS.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/PROJECTS.md) / [BACKLOG.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/BACKLOG.md) のステータスを基準としてください。

### 成熟度マーク

| マーク | 意味 |
| --- | --- |
| 🟢 | コミュニティ初期版として利用可能：主要フローが通り、コミュニティでの利用が始まっており、継続的に改善中 |
| 🔵 | 開発中：主要機能が実装され、実機でのイテレーションを継続中 |
| 🟡 | 設計中 / 初期版：スケルトンまたはプロトタイプであり、フローはまだ未完成 |
| ⚪ | 担当決定済み（Claimed）、着手待ち |
| ⬜ | 募集中：固定のメンテナーがまだ不在 |

### プロダクト機能の制約事項（必ずお読みください）

- **医療機器ではありません**：診断・治療の提案・効果判定は行わず、病院のシステムや医師を代替しません。
- **解析成功 ≠ 構造化成功**：MinerU/OCR は原本の品質、Token／同意、ドキュメント種別の影響を受けます。抽出候補が 0 件となる場合もあり、解析テキストの確認や手動追加入力が必要です。
- **AI は「読み取りと候補の提案」のみ**：事実データベースへ直接書き込みません。承認／修正／却下は人が行います。
- **AI 自動登録はまだ完全自動化されていません**：公開セッション契約には下書きと送信のみがあり、応答完了イベントがありません。現在は「手動インポート／応答貼り付け」であり、ホスト側で `completed` イベントが補完された後に自動解析を実装予定です。
- **ナレッジベース・一括インポート・複数ファイル・AI 抽出は継続開発中**：すべてのワークベンチに実装されているわけではありません。
- **データは原則ローカル保存**：クラウド解析や外部 API を使用する場合はユーザーの同意が必要であり、送信範囲を明示します。
- **疾患カバー率はまだ不完全です**：「あらゆる疾患でそのまま使える完成品」とはみなさないでください。

### 初期バージョンの目標：共同開発者への足がかり

私たちはこれを「完成品発表会」ではなく、**取り組みやすい足がかり**にしたいと考えています：

- **希少疾患コミュニティのパートナー**：疾患の知見を持ち寄り、フロー・項目・案内文言・実シーンを補完する。
- **開発者**：モジュールの追加、OCR/MinerU/ナレッジベース/API の接続、バグ修正を行う。
- **患者ご家族 / ボランティア**：試用、ヒアリング、コンテンツの校正、トレーニングの実施（コードを書かなくても貢献できます）。
- **医療従事者 / 研究者**：医学的ロジックを校正し、やってはいけないこと・できないことの境界線を指摘する。

## 主な特徴

1. **DSH Desktop ワークベンチ** —— デスクトップホストを通じて、疾患別の業務パネルとプラグイン機能を搭載。
2. **患者シーン駆動** —— 「小胰宝」などの疾患ワークベンチをモデルケースとして、患者とご家族の情報管理フローを継続的に改善。
3. **出典のトレーサビリティ** —— 医学コンテンツには出典とバージョンを明記し、未検証項目は明確に表示、診療提案は生成しません。
4. **診療記録と指標の整理** —— 病歴、検査資料、受診時の質問を中心とした整理機能を提供。具体的な対応範囲は各ワークベンチの説明と検証ステータスに準拠します。
5. **拡張可能なプラグイン機構** —— `cordis.patch.yml` の `insert` エントリまたは DSH のプラグインインストール窓口からサードパーティプラグインを接続。DSH Desktop 内では一律にアプリ内のワークベンチマーケット／インストール済み一覧を使用し、別途 Web 画面は立ち上げません。
6. **多言語とローカライズ** —— 中国語ローカライズを内蔵し、ドキュメントと UI はさらに多くの言語へ順次拡張中です。

## アーキテクチャ概要

**ワークベンチを核とし、下位で基盤機能に接続し、上位でエンドユーザーアプリを支える構成です。AI とワークベンチは双方向連携し、MinerU は解析のみを担当します。**


- **AI ↔ ワークベンチ**：ワークベンチはプロンプト、確認済み事実、検索スニペットをネイティブセッションへ渡し、AI は候補／解説のみを返して事実データベースへは直接書き込みません。
- **MinerU パイプライン**：原本 → MinerU 一括解析 → markdown/content_list → `parsed/<docId>.md` + 候補 → 人による確認 → SQLite 事実層。
- **ランタイム**：これは論理レイヤー図であり、プロセス図ではありません。ワークベンチは profile 内の DSH プラグインであり、サーバー側は Harness プロセス、Panel は Harness Web UI、業務ページは iframe 上で動作し、ネイティブセッションはホストから渡されます。資料はワークベンチ独自の workspace に保存されます。詳細は [ARCHITECTURE.md §2.2](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/ARCHITECTURE.md#22-运行时映射工作台作为-dsh-插件) を参照してください。
- **データプレーン**：ワークベンチの SQLite はユーザーが選択した資料ディレクトリ（例：`pinkypal.sqlite`）に置かれ、DSH profile やセッション DB には保存されません。AI が直接これを開くことはありません。
- **AI 書き戻し**：AI の応答は候補としてのみ扱われ、ワークベンチ API と人による確認を経て初めて SQLite に書き込まれます。デフォルトでは SQL／コード書き込みツールを提供せず、フロントエンドも変更しません。
- アーキテクチャ全体および AI から SQLite への書き込み経路の詳細は **[ARCHITECTURE.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/ARCHITECTURE.md)** をご覧ください。

### インストール（DSH Desktop、推奨ルート）

1. [DSH Desktop 公式サイト](https://dshdesktop.com/zh/) から **DSH Desktop** をインストールして起動し、初回オンボーディングを完了します。
2. **設定 → 一般** で「ワークベンチ機能を有効にする」がオンになっていることを確認します（オフにするとすべてのワークベンチが読み込まれなくなりますが、既存のセッションとデータは影響を受けません）。
3. 左側の **ワークベンチマーケット** を開き、疾患ワークベンチ（例：「小粉宝」）を検索してインストールします。
4. 「ワークベンチのインストール変更を有効にするには Harness の再起動が必要です」と表示されたら **今すぐ再起動** をクリックします。表示されない場合はメニューの **Harness → Harness を再起動** を実行します。
5. マーケットに戻って **インストール済み** タブで項目を確認し、左側の固定入口から業務パネルを開きます。

> ⚠️ **`dsh web` で Web 版を起動し、ブラウザ上の Settings → Plugins からプラグインを切り替えないでください。** それは CLI / Web ホストであり、DSH Desktop とは別の Harness・別のインストール先になります。そちらに入れても Desktop 側では読み込まれません。Desktop の正規入口はアプリ内のワークベンチマーケット／インストール済み一覧のみです。

### コマンドラインインストール（開発者 / ローカル検証向け）

Desktop には Harness と pnpm が同梱されています。コマンドラインからインストールする場合は、明示的に **Desktop の** Harness ディレクトリを指定する必要があります。そうしないと CLI の `~/.dsh` にインストールされ、Desktop から見えなくなります：

```bash
# macOS：Desktop の Harness ディレクトリ（他プラットフォームはアプリの「バージョン情報 / 診断」表示に準拠）
export DSH_HOME="$HOME/Library/Application Support/dsh-desktop/harness"
export PATH="$DSH_HOME/.desktop-bin:$PATH"   # アプリ同梱の pnpm / node を使用

dsh plugin add --help                        # 構文はローカルの help を確認し、推測しないこと
dsh plugin add ./dist/my-workbench-0.1.0.tgz
```

インストール後もアプリ内で Harness を再起動し、「インストール済み」で項目を確認する必要があります。**現在のバージョンでアプリ内のローカル `.tgz` インストール入口が提供されているかは「ワークベンチマーケット／インストール済み」で実地確認してください。** 入口がないバージョンでは無理に探さず、上記のコマンドライン方式を直接使用してください。

> つまずきやすい 3 つの落とし穴：
> ① **Desktop の Harness は `~/.dsh` ではありません**。macOS ではデフォルトが `~/Library/Application Support/dsh-desktop/harness` であり、アクティブな profile ディレクトリ名も同じく `web` です——名前が同じでも場所が異なります。`~/.dsh/profiles/*` に入れたものは Desktop では読み込まれません。パスはアプリの「バージョン情報／診断」の表示と実際の読み込み証拠を基準とし、ディレクトリ名で推測しないでください。
> ② `dsh --profile web --dump-config` にプラグイン層が表示されても設定の反映を証明するだけで、**UI 読み込みの証拠にはなりません**。
> ③ ワークベンチは Desktop の分離 generation インストールを経て `desktop-workbenches/market-installs.json` に記録されて初めて、クライアントからワークベンチとして認識されます。手動で `node_modules` に配置しただけでは左側の入口に表示されません。

### インストールの確認

| 証拠レベル | 確認方法 | 証明できること |
| --- | --- | --- |
| 設定層 | `dump-config` に本パッケージのプラグイン層がある | patch が有効であることのみを証明 |
| 一覧層 | アプリ内のワークベンチマーケット「インストール済み」に項目が出る | パッケージが認識され、登録に成功したことを証明 |
| 画面層 | 左側の入口から業務パネルを開き、主要フローが一通り操作できる | **唯一「インストール合格」とみなせる証拠** |

3 層すべてが揃って初めて完了となります。最初の 2 層しか確認できていない場合は「設定読み込み済み・UI 未検証」と記載し、「インストール合格」とは記載しないでください。

コード、ドキュメント、翻訳、Issue フィードバック、プラグインのインキュベーションなど、あらゆる形での貢献を歓迎します。

**患者ワークベンチの詳細な貢献ハンドブックは [CONTRIBUTING-WORKBENCH.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/CONTRIBUTING-WORKBENCH.md) にあります**（4 つの貢献ルート［疾患担当引き受け / モジュール / コンテンツ・医学照合 / スキャフォールド］、3 つのゲート、PR セルフチェックリスト、レビューチェックリストを含みます）。

### 貢献フロー

1. **担当引き受け（Claim）または Issue の起票**：[Issues](https://github.com/xyb-openharness-dsh-plugins/.github/issues) で検索または新規 Issue を作成し、要件や方針を議論します。疾患の担当を引き受ける場合は「病种认领（疾患担当引き受け）」テンプレートを使用し、Issue に `/claim` とコメントして取得を完了してください。
2. **Fork してブランチを作成**：対象リポジトリの `main` からフィーチャーブランチ（`feat/your-feature` や `fix/your-bug` など）を切ります。
3. **ローカル開発とセルフテスト**：本組織のプラグイン規約とコードスタイルに従い、既存のチェックと基本テスト（`npm run check`）が通ることを確認します。
4. **変更のコミット**：コミットメッセージは [Conventional Commits](https://www.conventionalcommits.org/)（`feat:`, `fix:`, `docs:` など）に準拠することを推奨します。
5. **Pull Request の作成**：変更の動機・範囲・検証方法を記載します。医療関連コンテンツを含む場合は、安全性とプライバシーへの配慮も追記してください。
6. **レビューとマージ**：1 名以上のメンテナーの承認後にマージされます（ゲートやデータ契約に関わる変更は 2 名の承認が必要です）。

> ⚠️ **品質基準**：`npm run check` の通過は V1 に過ぎません。V2（Desktop profile での実読み込み）と V3（実機での業務フロー完結）が必要であり、**3 層すべてが揃わなければ合格とみなしません**。**「PR がマージされた」ことは「リリース済み・検証済み」を意味しません。**

### 4 つの絶対原則

1. 診断および処置の提案を行わない（「治療を推奨／再発の可能性／休薬可能／受診不要／治癒率」などの表現を書かない）。
2. 患者データはローカルファーストとし、無断アップロードを導入しない。
3. 医学コンテンツには出典とバージョンを明記し、未検証項目には「未検証」と記載して隣接疾患からの外挿を行わない。
4. ガイドラインの臨床内容を複製せず、範囲参照として疾患名とバージョン番号のみを引用する。

### 行動規範

友好的・プロフェッショナル・包摂的な態度を保ってください。一般的なオープンソース行動規範に従い、あらゆるハラスメントや差別的言動を禁止します。

## プラグイン開発

DSH プラグインは本質的に [cordis](https://github.com/cordiverse/cordis) 規約に準拠した npm パッケージです。以下に最小構成で動作するプラグインのスケルトンを示します。

### 最小プラグインの例

`package.json`：

```json
{
  "name": "@your-scope/dsh-plugin-hello",
  "version": "0.1.0",
  "type": "module",
  "main": "lib/index.js",
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.1"
  }
}
```

`src/index.ts`（ビルド成果物は `lib/index.js` に出力）：

```ts
import { Context } from '@deepseek-ai/cordis'

export const name = 'hello'
export const using = [] as const

export function apply(ctx: Context) {
  ctx.on('ready', () => {
    console.log('Hello from your DSH plugin!')
  })
}
```

### DSH 設定への登録

プラグインパッケージを対象 profile の `node_modules` にインストールした後、`cordis.patch.yml` の `insert` エントリから読み込みます：

```yaml
# <対象 profile>/cordis.patch.yml
- insert:
    - id: hello
      name: '@your-scope/dsh-plugin-hello'
```

インストール方法は**対象ホスト**によって異なります（両者に互換性はありません）：

| ホスト | インストール方法 | 対象 profile（実際の読み込み先を基準とする） |
| --- | --- | --- |
| DSH Desktop | ワークベンチ：左側の「ワークベンチマーケット」から検索してインストールし、完了後 Harness を再起動<br>ローカル検証：`DSH_HOME` を Desktop Harness に向けた上で `dsh plugin add` | デフォルト `~/Library/Application Support/dsh-desktop/harness/profiles/web`（`~/.dsh` **ではない**） |
| CLI / Web | `dsh plugin add --help` で構文を確認した上でインストール | `~/.dsh/profiles/web` |

> ワークベンチ（workbench）は Desktop 側に**のみ**インストールできます。バンドルだけでなく、Desktop の分離 generation インストールフローを経て `desktop-workbenches/market-installs.json` に記録されることで初めて、クライアントがワークベンチとして認識します。`node_modules` に配置しただけでは左側の入口に表示されず、マーケットでも「インストール済み」として認識されません。

開発規約：

- プラグインのパッケージ名は識別と集約を容易にするため `@<scope>/dsh-plugin-<name>` 形式を推奨します。
- 必要な `peerDependencies`（`@deepseek-ai/cordis` や対応する `@deepseek-ai/dsh-client-*` など）のみを宣言し、ホスト側との重複バンドルを避けてください。
- 医療などの機微なシーンに関わる場合、出力は説明可能かつ追跡可能であり、デフォルトでプライバシーを最優先する必要があります。
