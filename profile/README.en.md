## Project Overview

**OpenHarness DSH Plugins** is a patient workbench and plugin community jointly built by xtra-care community and [Dataelem](https://github.com/dataelement). Workbenches run on [DSH Desktop](https://github.com/dataelement/dsh-desktop), maintained by Dataelem, organizing medical records, disease timelines, and visit preparation around real patient scenarios.

**DSH Desktop by Dataelem** is a desktop Agent application developed by the Dataelem team on top of upstream [DeepSeek Harness](https://github.com/deepseek-ai/dsh); it is not an official DeepSeek desktop product. xtra-care community contributes patient scenarios and domain experience, while Dataelem provides the desktop host, workbench framework, and productization support—together refining reference templates and reusable scaffolds.

Rooted in "**public interest and open source**," our flagship project **XiaoYiBao (小胰宝)** and disease-specific workbenches focus on information organization, disease-course logging, biomarker tracking, and consultation preparation, helping patients and families manage records and communicate more clearly. Workbenches do not provide diagnosis, treatment, or clinical management advice, and do not replace physician judgment.

**Core Goals:**

- **Open Ecosystem**: Open to researchers, clinical engineers, and developers—anyone can contribute plugins following unified specifications.
- **Safe & Explainable**: Outputs include supporting evidence and reference sources, with privacy first to prevent leakage of identifiable information.
- **Highly Extensible**: Modular plugin mechanism for easily integrating new models, data sources, and scenarios.
- **Community-Driven**: Encouraging clinicians, researchers, and developers to collaborate so technology becomes a bridge between people and hope.

## Current Release Boundaries and Co-Building Invitation

### Upfront Clarity: Not Every Disease Is Ready Out of the Box

- **Rare diseases and some cancer types not yet covered by the community**: Still in the skeleton, design, or recruiting stage, with incomplete features and content.
- **Published workbenches**: Vary in maturity—some are ready for daily use, while others are initial clickable prototypes.
- **Across workbenches**: Data models, fields, and import/parsing capabilities may differ; refer to each repo's README and [PROJECTS.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/PROJECTS.md) / [BACKLOG.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/BACKLOG.md) for current status.

### Maturity Badges

| Badge | Meaning |
| --- | --- |
| 🟢 | Community early release usable: core flows work end-to-end, already in community use, actively iterating |
| 🔵 | In active development: major features implemented, iterating on real devices |
| 🟡 | In design / early prototype: skeleton or prototype, flows not yet complete |
| ⚪ | Claimed, pending kickoff |
| ⬜ | Recruiting: no dedicated maintainer yet |

### Product Capability Constraints (Read First)

- **Not a medical device**: Does not diagnose, recommend treatments, or evaluate efficacy; does not replace hospital systems or physicians.
- **Parsing success ≠ structuring success**: MinerU/OCR depends on source document quality, token/consent, and document type; it may yield 0 candidates, requiring review of parsed text or manual entry.
- **AI only "reads and proposes candidates"**: It never writes directly to the fact store; acceptance, editing, or rejection is performed by humans.
- **AI auto-ingestion is not yet closed-loop**: The public session contract only covers drafting and sending, without a completion reply event; currently users manually import/paste replies, and automatic parsing will be added once the host provides the `completed` event.
- **Knowledge base, batch import, multi-file, and AI extraction are still iterating**: Not all workbenches have these yet.
- **Local-first data by default**: Cloud parsing or external APIs require user consent with clear disclosure of what is sent.
- **Incomplete disease coverage**: Do not treat this as a product where "every disease works immediately."

### Goal of the Initial Release: A Stepping Stone for Co-Builders

We want this to be not a "finished product launch," but an **accessible stepping stone**:

- **Rare-disease community partners**: Bring disease-specific knowledge to fill in workflows, fields, phrasing, and real-world scenarios.
- **Developers**: Build modules, integrate OCR/MinerU/knowledge bases/APIs, and fix bugs.
- **Patient families / volunteers**: Test, conduct interviews, proofread content, and organize training—no coding required to contribute.
- **Clinicians / researchers**: Review medical logic and define boundaries of what should and should not be done.

Where to start: Check [PROJECTS.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/PROJECTS.md) for active diseases → [BACKLOG.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/BACKLOG.md) for gaps and claims → [CONTRIBUTING.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/CONTRIBUTING.md) to pick a path → [CONTRIBUTING-WORKBENCH.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/CONTRIBUTING-WORKBENCH.md) for gates and PR self-checks.

## Key Features

1. **DSH Desktop Workbenches** — Hosts disease-specific business panels and plugin capabilities inside the desktop shell.
2. **Patient-Scenario Driven** — Uses "XiaoYiBao" and other disease workbenches as templates to continuously refine information-management workflows for patients and families.
3. **Traceable Sources** — Medical content cites sources and versions; unverified items are explicitly marked, and no clinical advice is generated.
4. **Medical Record & Biomarker Organization** — Builds capabilities around disease timelines, test reports, and visit questions; exact support depends on each workbench's docs and verification status.
5. **Extensible Plugin Mechanism** — Integrates third-party plugins via `cordis.patch.yml` `insert` entries or DSH plugin installation; inside DSH Desktop, always use the app's Workbench Market / Installed list rather than spinning up a separate Web UI.
6. **Multilingual & Localization** — Built-in Chinese localization, with ongoing expansion of documentation and UI into more languages.

## Architecture Overview

**The workbench sits at the core, connecting downward to foundational capabilities and upward to client apps; AI interacts bidirectionally with the workbench, while MinerU handles parsing only.**

```text
┌────────────────────────────────────────────────────────────────────┐
│ Client Application Layer                                           │
│   Harness Web UI (inside Desktop; standalone Web deployed separately)│
│   DSH Desktop (Workbench Panel) · Future: Mobile/MiniApp (via Host)│
└───────────────────────────────┬────────────────────────────────────┘
                                │
┌───────────────────────────────▼────────────────────────────────────┐
│ Workbench Core                                                     │
│   Shell: customFrame / Native Session Binding / Permissions & Audit│
│   Domain: Multi-Profile · Timeline & Labs · Records · Visit Prep   │
│           Candidate Review · Export · Psych Support (Companionship │
│           → Palliative → Grief) · Nutrition · Trial Matching       │
│           Drug Lookup · Complication Mgmt · More (expanding)       │
└───────┬───────────────────┬───────────────────┬────────────────────┘
        │ Bidirectional     │ Originals / Batch │ Search / Index
┌───────▼────────┐  ┌───────▼────────┐  ┌───────▼────────┐
│ AI Integration │  │ MinerU (Ext.)  │  │ Knowledge Base │
│ Native Session │  │ OCR/Layout/Tbl │  │ Files + FTS5   │
│ Bg Tasks TBD   │  │ markdown/JSON  │  │ Future Vector  │
└───────┬────────┘  └───────┬────────┘  └───────┬────────┘
        │                   │                   │
┌───────▼───────────────────▼───────────────────▼────────────────────┐
│ Future APIs: knows API · XYB RAG API · Multi-OCR · Psych/Nutr/Img/Gene│
└────────────────────────────────────────────────────────────────────┘
```

- **AI ↔ Workbench**: The workbench passes prompts, confirmed facts, and retrieved snippets to the native session; AI only returns candidates/explanations and never writes directly to the fact database.
- **MinerU Pipeline**: Originals → MinerU batch parsing → markdown/content_list → `parsed/<docId>.md` + candidates → human confirmation → SQLite fact layer.
- **Runtime**: This is a logical layering, not a process diagram. A workbench is a DSH plugin inside a profile—its server runs in the Harness process, its panel in Harness Web UI, its business page in an iframe, and the native session is passed by the host; data lives in the workbench's own workspace. See [ARCHITECTURE.md §2.2](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/ARCHITECTURE.md#22-运行时映射工作台作为-dsh-插件).
- **Data Plane**: The workbench SQLite database lives in the user-selected data directory (e.g., `pinkypal.sqlite`), not in the DSH profile or session store; AI never opens it directly.
- **AI Write-Back**: AI replies only produce candidates, which are written to SQLite only via workbench APIs + human confirmation; no SQL/code write tools are exposed by default, and frontend code is not modified.
- See **[ARCHITECTURE.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/ARCHITECTURE.md)** for the full architecture and the underlying path for AI writes to SQLite.

## Quick Start

### System Requirements

| Item | Requirement | Notes |
| --- | --- | --- |
| **DSH Desktop** | Latest stable release | **Recommended host**. Workbench and plugin installation and loading happen inside the app; bundles Node and pnpm, no separate install needed |
| Node.js | ≥ 18 (20 LTS recommended) | **Only needed for development or CLI host**, not for Desktop users |
| Package Manager | pnpm (bundled with Desktop) | Use `pnpm pack` for dev packaging |
| Git | Any recent version | Cloning repos and contributing |

### Installation (DSH Desktop, Recommended)

1. Install and launch **DSH Desktop** from the [DSH Desktop official site](https://dshdesktop.com/zh/), and complete initial onboarding.
2. Go to **Settings → General** and verify that **"Enable Workbench Feature"** is turned on (turning it off prevents all workbenches from loading, while existing sessions and data remain intact).
3. Open **Workbench Market** on the left sidebar, search for a disease workbench (e.g., "小粉宝" / PinkyPal), and install it.
4. When prompted that "Workbench installation changes require restarting Harness to take effect," click **Restart Now**; if no prompt appears, use the menu **Harness → Restart Harness**.
5. Return to the market, switch to **Installed** to verify the entry, then open the business panel from the pinned left-sidebar shortcut.

> ⚠️ **Do NOT run `dsh web` to launch the web version and toggle plugins under Settings → Plugins in a browser.** That is the CLI / Web host—it is not the same Harness or installation location as DSH Desktop, and Desktop will not load anything installed there. The official entry point for Desktop is strictly the in-app Workbench Market / Installed list.

### CLI Installation (Developers / Local Self-Testing)

Desktop bundles its own Harness and pnpm. CLI installation must explicitly point to **its** Harness directory, otherwise it installs into CLI's `~/.dsh` (invisible to Desktop):

```bash
# macOS: Desktop's Harness directory (on other platforms check "About / Diagnostics" in the app)
export DSH_HOME="$HOME/Library/Application Support/dsh-desktop/harness"
export PATH="$DSH_HOME/.desktop-bin:$PATH"   # Use the app's bundled pnpm / node

dsh plugin add --help                        # Check local help for exact syntax; do not guess flags
dsh plugin add ./dist/my-workbench-0.1.0.tgz
```

After installing, return to the app to restart Harness and verify the entry under **Installed**. **Check in-app under "Workbench Market / Installed" whether the current version provides a local `.tgz` install button**; if your version does not have one, use the CLI method above directly.

> Three common pitfalls:
> ① **Desktop's Harness ≠ `~/.dsh`**. On macOS it defaults to `~/Library/Application Support/dsh-desktop/harness`, and its active profile directory also happens to be named `web`—same name, different path. Anything installed into `~/.dsh/profiles/*` will not be loaded by Desktop. Always verify the path via "About / Diagnostics" in the app and actual load evidence rather than guessing by directory name.
> ② Seeing the plugin layer in `dsh --profile web --dump-config` only proves the config took effect—it **cannot** be used as evidence that the UI loaded.
> ③ A workbench must go through Desktop's isolated generation install and be recorded in `desktop-workbenches/market-installs.json` for the client to recognize it as a workbench; dropping files into `node_modules` manually will not make it appear in the left sidebar.

### Verifying the Installation

| Evidence Layer | What to Check | What It Proves |
| --- | --- | --- |
| Config Layer | Package's plugin layer appears in `dump-config` | Only proves the patch took effect |
| List Layer | Entry appears under "Installed" in the in-app Workbench Market | Proves the package was recognized and registered |
| UI Layer | Business panel opens from the left-sidebar entry and core flows work | **The ONLY evidence that counts as "installation passed"** |

All three layers are required; if you only verified the first two, report "config loaded, UI unverified"—never report "installation passed."

## Patient Workbench Roadmap (Goals and Recruiting)

We are building "local-first" patient workbenches disease by disease (record organization · biomarker tracking · visit preparation; no silent patient data uploads, and any external model/service call must clearly disclose what is sent). The target pool references the **NCCN Guidelines® disease catalog (67 entries)** and the **Compendium of 86 Rare Disease Diagnosis & Treatment Guidelines (2025 Edition)** (**153 items** total), focused on empowering patient self-management and rapid clinician review.

## Contributing

We welcome all forms of contribution: code, documentation, translations, Issue feedback, and plugin incubation.

**For the detailed patient workbench contributor handbook, see [CONTRIBUTING-WORKBENCH.md](https://github.com/xyb-openharness-dsh-plugins/.github/blob/main/CONTRIBUTING-WORKBENCH.md)**, covering the four contribution paths (disease claim / module / content & medical review / scaffold), three gates, PR self-check list, and review checklist.

### Contribution Workflow

1. **Claim or open an Issue**: Search or create an issue in [Issues](https://github.com/xyb-openharness-dsh-plugins/.github/issues) to discuss needs and proposals; to claim a disease, use the "Disease Claim" template and comment `/claim` on the Issue.
2. **Fork and create a branch**: Branch off `main` in the target repo, e.g., `feat/your-feature` or `fix/your-bug`.
3. **Local development and self-testing**: Follow the org's plugin conventions and code style, and ensure existing checks and basic tests pass (`npm run check`).
4. **Commit changes**: Follow [Conventional Commits](https://www.conventionalcommits.org/) (e.g., `feat:`, `fix:`, `docs:`).
5. **Open a Pull Request**: Describe the motivation, scope, and verification method; for medical-related changes, also note safety and privacy considerations.
6. **Review and merge**: Requires approval from at least one maintainer (two for changes affecting gates or data contracts).

> ⚠️ **Quality Bar**: Passing `npm run check` is only V1; V2 (real loading in Desktop profile) and V3 (end-to-end business loop on a real device) are also required—**all three layers must pass**. **"PR merged" does not equal "live / verified."**

### Four Non-Negotiables

1. No diagnosis or clinical management advice (never write "recommend treatment / likely recurrence / may stop medication / no need to see a doctor / cure rate").
2. Patient data is local-first; never introduce silent uploads.
3. Medical content must cite source and version; mark unverified items as "Unverified" and never extrapolate from adjacent diseases.
4. Never copy clinical guideline content—only reference disease names and version numbers as scope markers.

### Code of Conduct

Please be friendly, professional, and inclusive. We follow standard open-source codes of conduct and prohibit any form of harassment or discrimination.

### Signing & Licensing

Before submitting a contribution, verify the actual license and contribution terms published by the target repository and confirm you have the right to grant those rights; for repos without a published license, contact a maintainer first.

## Plugin Development

DSH plugins are essentially npm packages conforming to the [cordis](https://github.com/cordiverse/cordis) specification. Below is a minimal runnable plugin skeleton.

### Minimal Plugin Example

`package.json`:

```json
{
  "name": "@your-scope/dsh-plugin-hello",
  "version": "0.1.0",
  "type": "module",
  "main": "lib/index.js",
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.1"
  }
}
```

`src/index.ts` (compiled output to `lib/index.js`):

```ts
import { Context } from '@deepseek-ai/cordis'

export const name = 'hello'
export const using = [] as const

export function apply(ctx: Context) {
  ctx.on('ready', () => {
    console.log('Hello from your DSH plugin!')
  })
}
```

### Registering in DSH Configuration

Once installed into the target profile's `node_modules`, the plugin is loaded via an `insert` entry in `cordis.patch.yml`:

```yaml
# <target profile>/cordis.patch.yml
- insert:
    - id: hello
      name: '@your-scope/dsh-plugin-hello'
```

Installation method depends on the **target host** (the two are not interchangeable):

| Host | Installation Method | Target Profile (subject to actual loading) |
| --- | --- | --- |
| DSH Desktop | Workbench: search and install in left-sidebar "Workbench Market," then restart Harness<br>Local self-test: point `DSH_HOME` to Desktop Harness, then run `dsh plugin add` | Defaults to `~/Library/Application Support/dsh-desktop/harness/profiles/web`, **NOT** `~/.dsh` |
| CLI / Web | Check syntax with `dsh plugin add --help`, then install | `~/.dsh/profiles/web` |

> Workbenches can **only** be installed on the Desktop side: beyond the bundle, they must go through Desktop's isolated generation install and be recorded in `desktop-workbenches/market-installs.json` for the client to recognize their workbench identity. Dropping files into `node_modules` alone will not make them appear in the left sidebar or show as "Installed" in the market.

Development conventions:

- Name plugin packages as `@<scope>/dsh-plugin-<name>` for easy identification and aggregation.
